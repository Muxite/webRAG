# DAG v2 playbook/race-merge run — reasoning diff findings (2026-08-21)

Source: `dag_v2_playbook_race_20260821_*` result + `*_report_v3` files (full prompt/completion capture) in `agent/idea_test_results/`.

Arm-to-config mapping confirmed from scores + decision traces: `cfg370b23e7` (graph, `tooling_profile: full`) = `good_adaptive`; `cfgcb42ed79` (graph, same profile) = `good_adaptive_playbook`; `langgraph_react` cfg370b23e7 = `langgraph_react`.

## 1. Task 150 (race-merge, gpt-4.1-nano): langgraph_react 1.00 vs good_adaptive_playbook 0.33

**langgraph_react (score 1.00).** 3 LLM calls total. Call 1: empty completion, issued 3 search tool calls (Serper). All 3 searches returned **HTTP 403** (events 3–5 in the raw connector log — Serper is broken for this whole run, see §3). Call 2: still empty completion, but the model then issued 3 direct `ConnectorHttp` GETs to Wikipedia URLs it constructed itself (`en.wikipedia.org/wiki/Hardanger_Bridge`, the "list of longest suspension bridge spans" page, and the Norwegian `Hardangerbrua` page) — all 3 returned HTTP 200. Call 3 (prompt = 18,368 chars, all three pages' text concatenated into context): produced the final answer directly, correctly reading "Longest span 1,310 metres" out of the infobox (distinct from "Total length 1,380 metres" one line above, which the task explicitly warns against). Final deliverable cites all 3 URLs and states they agree at 1,310 m. **Mechanism**: when its search tool failed, the ReAct loop fell back to guessing canonical Wikipedia URLs directly and fetching them in one batched turn — not a race/merge abstraction, just tool-call resilience plus correct infobox-field discrimination.

**good_adaptive_playbook (score 0.33).** 9 LLM calls, 309 raw events. Expansion (event 7) produced 5 ordinary candidates (2 search, 3 visit) — **none carried the `race_group` or `alternative_of` field** that the system prompt describes as the opt-in race/merge tag. The engine treated them as normal GoT children, scored/selected them one at a time (0.9/0.1/0.1/0.1). Both searches came back `success: true, url: None` (Serper 403 masked as an empty-but-non-error result — a swallowed-failure bug, see §3). The two `visit` actions that did fire both resolved to **`https://simple.wikipedia.org/wiki/Brooklyn_Bridge`** and **`https://en.wikipedia.org/wiki/Brooklyn_Bridge`** — an unrelated bridge, not Hardanger — even though the LLM's own link-selection call (event 149) had picked `https://en.wikipedia.org/wiki/Hardanger_Bridge`. That selected URL was never the one actually fetched. The grounding check only looks at `distinct_visits >= 1` and doesn't check subject relevance, so 2 off-topic Brooklyn Bridge visits were marked `grounded: real page evidence present`. A subsequent evaluation call (event 278) correctly scored the Brooklyn Bridge content 0.1 confidence as irrelevant, but the finalize-stage summarizer (event 298) then **hallucinated** "all three routes … confirm 575 meters" — a number that appears nowhere in any actually-fetched page — with `goal_achieved: true`. The very last synthesis call (event 308) somehow corrected the number to 1,310 m (evidently pulled from the model's own parametric knowledge, not from the garbage context), but the final deliverable text contains **zero source URLs**. Validation: keystone_main_span passes (1.0, right number by luck/prior knowledge) but route_coverage, route_agreement, and citations all score 0.0 → overall 0.33.

**Concrete answer to "why 0.33 not 1.00":** two independent, stackable defects, not a reasoning-quality gap:
- **Link-selection/visit-URL bug**: the LLM's chosen URL (Hardanger Bridge) was discarded and the executor visited an unrelated page (Brooklyn Bridge) twice instead. This needs root-causing in the visit-URL resolution path (whatever populates the `url` on the `action: visit` decision step) — it did not match `selected` from event 149.
- **The race-merge mechanism (`race_group`) never fired** on the flagship task it was built for. The model never emitted the tag in any of the 3 completions inspected (task 150 x2 arms, task 122). The candidates were still parallel-explorable (5 siblings authored, `execute_all_children` presumably false since only 2 fired sequentially per the decisions trace `selection`/`action` pairs), so this ran as ordinary sequential/best-first GoT search, not a concurrent race.
- Independently, citations were dropped from the final text even where the number was right, and the finalize step fabricated route agreement not supported by evidence — the grounding gate that should have caught "0 relevant routes visited" instead passed on visit-count alone.

## 2. Task 065 (chain, gpt-4.1-nano): near-total failure across the board

good_adaptive_playbook: 0.00, 0 visits at all. langgraph_react: 0.29 (partial credit), 2 visits. Both hit the **same Serper 403** (confirmed in both raw event logs, and also present in `good_adaptive`'s (non-playbook) 150 run — 2x 403 status entries — so this is a run-wide search outage, not arm-specific).

- **good_adaptive_playbook**: only 1 search attempt logged, 403, and the engine gave up — 0 visits, `goal_achieved: false`. To its credit, a grounding-scrub step correctly stripped the fabricated citations from the final text (`final_deliverable` literally says "**Insufficient grounded evidence** … Any specific value … may be fabricated" and shows `[unverified source removed]` markers), but the underlying elevation value it still reported, 110 m, is hallucinated (correct answer is 162 m).
- **langgraph_react**: also hit the search 403, but (unlike task 150) had no guessable canonical URL to fall back to for "elevation of Pablo Neruda's birth town," so it explicitly told the user "direct online sources are not providing the elevation, I will rely on my knowledge" and guessed 124 m (wrong; correct is 162 m). It still got partial credit because it correctly chained poet → Parral, Chile with some page evidence along the way (chain_coverage 0.5, visit_count 0.67).

**Verdict**: this is **not purely a hard-task signal** — it is substantially confounded by the same live Serper 403 outage that hit task 150. The 0.00 vs 0.29 gap is largely explained by langgraph_react's different failure-recovery behavior (confident wrong guess with partial chain credit) vs good_adaptive_playbook's total shutdown (0 visits) rather than by either arm's core reasoning quality on the chain shape itself. The task may still be independently hard (both arms landed on a wrong final number even when they had some real evidence), but the near-zero scores can't be read as a clean quality comparison given the shared infra failure.

## 3. Shared infrastructure bug: Serper search returning HTTP 403

Confirmed via raw `connector_io` events in every result file inspected (task 150 both graph configs + langgraph_react, task 065 playbook config): every `ConnectorSearchSerper` call in this run returned `status: 403, error: True`. This is a real, run-wide search-backend failure, independent of the playbook/race-merge mechanism under test. Two different failure-swallowing behaviors compound the damage:
- On `good_adaptive`/`good_adaptive_playbook`, a failed search is recorded as `action: search, success: true, url: None` — success even though nothing usable was returned — which then let downstream visit-URL resolution silently substitute an unrelated URL (Brooklyn Bridge, task 150) instead of raising/replanning.
- `langgraph_react` degrades more gracefully by falling back to direct URL construction/fetch when the entity is Wikipedia-guessable (task 150), but has no such fallback for less guessable facts (task 065's elevation), and openly admits when it's guessing from memory instead of grounded evidence.

## 4. Task 122 (alt-branch, llama-3.2-3b): good_adaptive_playbook 0.80 vs good_adaptive 0.50 — confirmed real

`good_adaptive` (cfg370b23e7): expansion produced only **1** candidate (jumped straight to "confirm FAST telescope," skipping any actual comparison), 1 visit, `branch_exploration` 0.25 (1/4 telescopes resolved from visited pages).

`good_adaptive_playbook` (cfgcb42ed79): expansion produced **4** candidates — one visit-with-URL per telescope (Arecibo, RATAN-600, Green Bank, FAST) — and all 4 were actually visited (decisions trace shows 4 consecutive `action: visit` entries right after expansion), giving `branch_exploration` 1.0 (4/4 resolved) and a correctly named survivor (FAST) with grounded evidence. Citations still scored 0 (same URL-not-in-final-text pattern as task 150).

This improvement is real and traceable to broader branch exploration at the expansion step (4 candidates authored and executed vs 1). However, **no completion in any of the 3 inspected tasks (150 x2, 122) ever emitted the `race_group` or `alternative_of` tag**, and no prompt in any of them contained dynamically injected "playbook advice" text (checked literal strings `playbook`/`advice`/`Playbook` in the full prompt bodies — zero hits in all cases; only the static system-prompt boilerplate describing the two optional fields was present, identical across both arms). So the task 122 win is real, but it is **not evidence that the playbook-advice-injection or race_group/alternative_of tagging mechanisms are doing anything** — whatever changed candidate count from 1→4 between `cfg370b23e7` and `cfgcb42ed79` is a different config-level knob (breadth/candidate-cap policy bundled into that config hash), not the advertised new mechanism.

## What this means for the next cycle

1. **Concrete bug, not a tuning gap**: the visit-URL resolution path used a URL other than the one the model selected (Brooklyn Bridge instead of the LLM's chosen Hardanger Bridge URL) in task 150's playbook run. This is reproducible from the decision trace (`selection`/`action` mismatch) and should be root-caused directly — find what populates `url` on the `action: visit` step when the preceding `search` action returned `url: None`.
2. **The race_group/alternative_of mechanisms appear unused in this entire sample** (3/3 tasks checked, including the one purpose-built to exercise them). Before any more tuning, instrument/log whether these fields are ever emitted at all across a larger sample — if the rate is near-zero, the problem is prompt salience/framing (the instructions are static boilerplate, buried in a long system prompt, with no worked example), not model capability.
3. **Grounding check is too weak**: it counts `distinct_visits` without checking subject relevance, letting 2 off-topic page visits pass as "grounded: real page evidence present." This directly enabled the finalize-stage hallucination ("575 meters," 3 routes agreeing) in task 150. Tightening this gate (e.g., requiring the visited page's title/content to match the mandate's named entity) would likely have forced a replan instead of a confident wrong/fabricated synthesis.
4. **The Serper 403 outage is a confound, not a finding** — it affected both graph arms and even degraded langgraph_react. Task 065's near-zero scores across arms should not be read as a chain-shape capability signal until the run is repeated with a working search backend. Task 150's result is still meaningful (both arms hit the same search outage, but only the playbook arm's downstream visit-URL handling produced a wrong page + a scrubbed-but-still-partly-fabricated citation gap), so its findings above stand independent of the outage.
5. Silent failure-swallowing (`search succeeded, url: None`) should raise/replan instead of falling through to a corrupted downstream state; this is a second, cheaper fix (search failure handling) that's separable from the URL-resolution bug in #1.
