### Two corrections that matter

**1. PIVOT's title.** The paper is *"PIVOT: Bridging Planning and Execution in LLM Agents via
Trajectory Refinement"* (Tuo Zhang, Popa, Xu, Song, Dimitriadis; arXiv 2605.11225, v1 11 May 2026,
not withdrawn). "Plan-Inspect-eVOlve Trajectories" is the **in-body acronym expansion, not the
title** — cite it as such. Backbone claim holds verbatim: *"We instantiate all methods on the same
set of underlying model backbones, including Qwen3-235B, Claude 4.5 model family, and Claude 4.6
Opus."* Benchmarks DeepPlanning and GAIA. **Nothing <=14B.**

**2. A NEAR-MISS that constrains our negative claim.** **Reason-Plan-ReAct (arXiv 2512.03560)**
compares a planner/executor split against a ReAct baseline on six open-weight models **including
Qwen3-14B and DeepSeek-R1-Distill-Qwen-7B**. It is not our exact cell — enterprise tasks not
web-grounded, separate reasoner and planner roles, and no same-model-as-judge. But it means the
bare claim *"no published result compares a planner/executor split to ReAct on <=14B open models"*
would be **FALSE**. Our claim survives **only with the web-grounded + same-model-as-judge qualifiers
kept intact.** Do not drop them.

### ReWOO's 7B planner, precisely
Alpaca-7B (LLaMA-based), further fine-tuned with **LoRA for 10 epochs on ~2,000 planning
trajectories bootstrapped from 4,000 generated by text-davinci-003**. This is a **distillation**
result. It is not evidence that structure alone lifts an untuned 7B, and it violates our
no-fine-tuning filter.

### One drift to guard against
The cookbook's *"brief granularity has an optimum"* is an observation about **worker brief size and
cost, from frontier-model runs**. It is NOT a small-model branching-factor measurement and must not
be allowed to drift into that role. No source was found measuring the branching factor a small model
emits under decomposition, nor supporting "fewer, larger steps are better" as a measured result.

## The review's central conclusion

> The DAG is not losing because it lacks more search, more reflection, or more sibling visibility.
> It is losing because it treats an N-row aggregation task as prose-tree planning and then destroys
> the rows during aggregation. For this task shape, build a **deterministic coverage executor with
> typed per-item extraction**; retain a linear ReAct-like loop for chains and open-ended discovery.

This aligns with our measured evidence rather than contradicting it, which is itself a caution —
agreement is easy to over-weight.

**Note (user):** the tree-search framing in parts of the review is not ours; ignore it. We are not
running rollout tree search.

## A. Coverage scheduling

**A1 — what assigns work.** Three controller types, different roles:

| Controller | Best use | Failure mode for us |
|---|---|---|
| Deterministic worklist/frontier | Task names N entities/fields/constraints | Needs a reliable list parser (tractable) |
| Coverage-deficit score | Known incomplete cells, several valid next actions | Can prioritise the wrong unknown unless very simple |
| LLM scheduler | Entity set genuinely unknown; needs hypothesis generation | Weak model omits entities, duplicates work, declares premature completion |

Recommended primitive:
```
For every requested entity i: create WorkItem(i, required_field_set)
For every unresolved (entity, field) cell: schedule evidence acquisition or conflict resolution
Terminate only when every critical cell is:
    SUPPORTED | CONTRADICTED | EXPLICITLY_UNAVAILABLE | BUDGET_BLOCKED
```
Framing: this is not "less agentic" — it moves a **mechanical invariant (coverage)** out of a weak
model's unreliable planning loop.

**Claim:** no clean published result showing distinct-source coverage scales monotonically with
fan-out width on the same weak local model. Closest is Anthropic's multi-agent report, which
attributes most BrowseComp variance to **token usage, tool calls and model choice — not fan-out**,
and warns that shared-context/high-dependency tasks fit multi-agent poorly.
*Our 84 visit nodes for 6 distinct URLs is exactly "width multiplies the same behaviour".*

**A2 — Anthropic's coordinator pattern does not transfer cleanly.** Real lessons: workers need an
objective, expected output, source guidance and a boundary; work should scale with query complexity;
parallelism suits independent directions; subagent outputs should become durable artifacts rather
than repeatedly traversing a lead transcript. **The omitted condition:** Anthropic says multi-agent
becomes valuable "once intelligence reaches a threshold" — their lead is Opus, workers are Sonnet.
Predicted same-weak-model failures: bad partitioning; vague briefs producing duplicate search;
compression loss of the discriminative value; budget spent judging rather than collecting;
judge-on-judge collapse; delegation floor cost; **no feedback reinvestment (matches our null)**.

Proposed transfer — deterministic coordinator, bounded model executor:
```
Coordinator (code): parse entities/fields, mint missing-cell jobs, dedupe targets,
                    maintain cell state, stop on coverage contract
Weak model:         formulate one query, choose among a small URL set,
                    extract a field from a page, classify a result/conflict
```

**A3 — deep-research systems.** No universal architecture. Units of work differ:

| System | Unit of work | Termination |
|---|---|---|
| ReAct | one next action conditioned on observation | model emits finish / budget |
| ReWOO | planned evidence slot `#E_i` | slots filled, then solve |
| Anthropic research | delegated research brief | lead judges sufficiency |
| PIVOT | candidate trajectory suffix | loss improves + global verify |
| **Proposed for us** | **(entity, field, source-policy) cell** | **mechanical coverage ledger** |

Shared pattern is not tree search: `decompose/enumerate -> acquire -> compact -> detect gaps ->
acquire more -> synthesize under an evidence check`.

## B. State representation and extraction

**B1 — extract-then-synthesize vs giant final prompt.** **Explicit gap:** no clean controlled paper
testing per-hop typed extraction vs one-shot long-context finalize, measuring extraction recall loss
on weak <=14B models. Surrounding evidence: Lost-in-the-Middle positional loss; map-reduce systems
exist to shorten context but acknowledge summarisation loses information; ReWOO's own error analysis
notes the solver can be wrong even when plan and evidence are sound.

Our pipeline is worse than a generic long-context problem — it is **repeated destructive compression
with no structured field preservation**:
```
Raw page -> 2,000-char child merge view -> 1,000-char merged-JSON compaction
        -> concat of ~5.3 pages -> hard 80,000-char stop -> prose synthesis
```
Proposed record (keep TWO channels — typed record AND a recoverable raw pointer; never summarise
away the only copy of a value):
```json
{"entity": "...", "field": "...", "value": "atomic or null",
 "verdict": "supported|absent|ambiguous|conflicting",
 "source_url": "...", "quote": "minimal exact span",
 "source_tier": "primary|maintained|secondary", "retrieval_timestamp": "ISO-8601"}
```

**B2 — LangGraph does not force an LLM join.** `Send` is an execution primitive; it does not
prescribe the join. Good pattern: map returns typed `ItemResult`; reducer appends, dedupes by
identity, updates coverage deterministically; synthesiser reads a compact typed table.
Dangerous pattern (ours): map returns prose, join prompt says "remove redundancy".
For aggregation, rows differing only in a number **look** redundant. **No published figure for
"LLM join loses X% per-item recall vs a typed reducer" — this is our experiment to run, not doctrine.**

**B3 — long-context ordering.** Ordering helps but cannot repair hard truncation or repeated lossy
merges. Use: stable row tags (`[entity=..][field=..]`); **table-first finalisation**; raw quotes only
for contested/critical fields; critical-at-edges packing; **stop adding raw pages BEFORE the typed
table, never after**. Suggested finalizer order: decision contract -> complete typed matrix ->
missing/conflicted matrix -> critical quotes -> optional excerpts -> answer schema.

## C. Weak-model planning — what survives review

**C1.** No paper supplies our exact cell: same untuned <=14B model as planner + executor +
judge/selector, web-grounded, vs plain ReAct.

| Method | What it establishes | Why it does not validate our DAG |
|---|---|---|
| ReWOO | Plan-Work-Solve beat ReAct on GPT-3.5, fewer tokens; HotPotQA 42.4% vs 40.8% | Main comparison GPT-3.5; **the 7B planner is FINE-TUNED/distilled from ~2,000 GPT-3.5 traces** |
| LATS | Tree search + LM value/reflection beats baselines | GPT-4-class; no evidence it survives an anti-calibrated weak judge |
| Reflexion | Verbal feedback improves agents | Depends on feedback quality; not evidence for a weak self-judge |
| PIVOT | Plan/inspect/evolve/verify helps constraint-heavy trajectories | Evaluated on **Qwen3-235B and Claude**, not <=14B |

ReWOO's 7B result **violates our no-fine-tuning filter**. LATS is least transferable: its selection
oracle is exactly what our merge AUC 0.288 says is anti-predictive here.

**C2 — ReWOO placeholders.** Main planner is GPT-3.5; the 7B planner is fine-tuned on ~2,000
GPT-3.5 trajectories. Reported qualitative failures: planner assumes a tool result contains a fact it
does not; full foresight impractical under unknown environments; solver fails on sound evidence; bad
tool results derail behaviour. **No reported malformed-placeholder rate, parser-repair rate, or #E
resolution failure rate.** => Treat "robust placeholder planning on weak models" as UNSUPPORTED.
Our safer form: references generated and resolved **by code**, not emitted as `#E7` prose.

**C3 — "0% structured output" is NOT substantiated as stated. REMOVE IT** unless we have our own
measurement. Closest real evidence: **JSONSchemaBench** — unconstrained empirical schema coverage
from ~90% on a function-call collection down to **13% (GitHub-Hard)** and **21% (JSONSchemaStore)**;
on **Llama 3.2 1B** grammar-constrained generation improved downstream accuracy ~**3pp** on three
small reasoning tasks; the paper distinguishes schema validity from semantic quality.
Defensible restatement: *small models can reason usefully while unconstrained structured-output
reliability degrades sharply as schemas get realistic; grammar constraints improve validity and can
improve downstream accuracy.* For qwen2.5:7b specifically — **benchmark it ourselves** with our exact
action schemas, nesting, enum count, context length, temperature and quantisation.

**C4 — PIVOT is real**: Plan-Inspect-eVOlve Trajectories, Zhang et al., 2026. INSPECT is **not purely
mechanical** — it computes/approximates a trajectory loss and uses LLM-generated structured feedback
as a textual-gradient-like signal; VERIFY is a global constraint check. Backbones Qwen3-235B and
Claude. **Take only the mechanical part:** preserve validated prefixes, repair the unsupported suffix,
identify the earliest failed evidence dependency mechanically. **Do not build textual-gradient
self-critique until our evaluator beats chance.**

**C5.** No convincing published positive result under all our filters (same fixed weak <=14B, both
roles, no fine-tuning, web-grounded, vs ReAct, gain attributable to structure alone).
**This absence is informative:** "planning is good for weak models" is NOT an established premise,
and our 59-task result is currently stronger evidence for our regime than the literature.
*Also flagged: our compiled-v1 result is the closer analogue to "strong planner, cheap executor";
DAG v2 is a different hypothesis and must not borrow compiled-v1's success as support.*

## D. Granularity

**D1.** No pre-2026-08-29 paper found justifying "fewer, larger steps are better" for weak
web-research models, nor measuring the branching factor a small model emits. Consensus is only that
granularity is a tradeoff. **Our data is stronger than the slogan**: 64% of expansions emit one
candidate; a width-1 expansion can terminate the run; aggregations need width and the prompt
suppresses it; root widening never fired in 59 runs. **Delete the rule.** Replace with a task-shape
contract: explicit enumeration of N entities -> mint N jobs immediately, do not ask the model whether
N branches deserve to exist; one unresolved chain dependency -> exactly one next-hop job; unknown
entity set -> bounded discovery jobs, then **freeze** the set before coverage collection.

**D2.** No direct benchmark for deterministic N-job minting vs LLM decomposition on this task family.
But dynamic map-reduce treats a state-determined worker count as first-class (LangGraph `Send`).
Prediction to test: deterministic minting helps aggregation/AND-filter, neutral on chains,
**eliminates the width-1 termination condition**.

## E. Weak judges and shared visibility

**E1.** No safe published capability cutoff for LLM value functions. Our own **merge AUC 0.288** is
conclusive enough: a below-chance ranking signal must not select branches, prune, allocate budget,
authorise early exit, or route "best child". Replace with mechanical signals:
```
+1 new canonical URL   +1 newly supported required cell   +1 new entity (discovery)
+1 verified contradiction resolved
-1 duplicate URL/content hash   -1 repeated query   -1 no actionable result   -1 unsupported extraction
```
An LLM may still extract/classify under constrained schemas; it must not be a scalar value oracle
until offline calibration earns it.

**E2.** No controlled paper isolating shared sibling visibility from budget/context/scheduling
changes. Better-supported practice is **isolated worker contexts + structured artifact exchange**,
not a pooled transcript. Our null is coherent: shared evidence -> less duplicate work -> fewer visits
-> **no rule that spends freed budget on missing cells** -> same coverage, same score.
**The missing mechanism is coverage-directed reinvestment**, not visibility:
`if duplicate suppression saves a visit: allocate one replacement visit to the highest-priority
unresolved cell.`

## F. When to stop using a graph

**F1.** A graph/parallel executor is justified only when ALL hold: N>=2 independently verifiable
obligations; independent evidence path per obligation; results representable as records and joinable
mechanically; final answer is a union/filter/count/argmax/comparison over those records; parallelism
buys wall-clock or more evidence per deadline; a deterministic coverage ledger can prove what remains
unresolved; final aggregation does not depend on one enormous raw concat.
**Not** justified merely because a task is hard, long or multi-step.
=> Do not abandon graph-shaped execution in principle. **Abandon the current
tree-plus-lossy-merge graph for coverage tasks.**

**F2.** No controlled public matrix comparing plain ReAct vs ReAct+adaptive mechanisms vs full graph
under the same model, tools, budget and task distribution. **This is our highest-value experiment**,
and our own engine review independently called it "the most interesting unmeasured cell".

## The decisive experiment matrix (2x2 factorial core)

`Scheduling in {linear, deterministic coverage}` x `Representation in {raw/prose, typed records}`

| Cell | Controller | Representation | Diagnostic |
|---|---|---|---|
| 1 | current `sequential_react` | linear scratchpad + raw observations | existing winning baseline |
| 2 | `sequential_react` | + typed extraction only | is finalisation/prose loss the main bottleneck? |
| 3 | deterministic N-job worklist | raw-page finalizer | is coverage scheduling alone enough? |
| 4 | deterministic N-job worklist | typed extraction + table-first finalizer | the full mechanical solution |
| 5 | as 4 | + constrained job/query selection | does weak-model adaptivity add value? |
| 6 | as 4 | + weak LLM deficit scheduler | likely NEGATIVE control |

Interpretation: typed records alone win -> the bug is finalisation/compaction. Coverage alone wins ->
the bug is work allocation. Only both -> complementary. Neither -> revisit retrieval/source selection
before touching planners. Constrained model scheduling loses to deterministic -> do not let a weak
model coordinate weak workers.

**Predicted:** Cell 4 produces the first meaningful recovery on aggregation tasks.

## Metrics — per-item, not just final score

```
supported-cell recall      = correctly supported required cells / required cells
distinct-source efficiency = supported cells / unique canonical visited sources
compression survival       = correct values in final table / correct values observed in visited pages
wasted-action rate         = duplicate or no-progress actions / all actions
```
`compression survival` is the one our current architecture cannot compute at all — we cannot tell
whether a missing row was never found, lost in merge compaction, cut by the 80k finalizer, or ignored
by synthesis.

## Bottom-line decisions proposed by the review

- Do NOT defend weak-model structure with LATS/ADaPT/Reflexion/Anthropic results — model and
  evaluator regimes do not match ours.
- Replace planner-created coverage with **deterministic obligation minting** whenever the task names
  entities/rows/fields/constraints/deliverables.
- Add **per-hop typed extractive records BEFORE any further scheduler work**.
- **Remove the merge judge from any gating or selection role** until it beats chance on a held-out
  calibration set.
- Use LLMs for **local** tasks: query reformulation, source choice, extraction, conflict explanation,
  final prose — never global coverage accounting.
- Make the next flagship baseline **`sequential_evidence_loop`** — it distinguishes whether the gap
  comes from graph topology or from missing typed state + extraction + deterministic coverage.
